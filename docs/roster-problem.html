Eduents · Architecture assessment

The Roster Problem

Classes, yearly promotion, roster-driven OMR scanning, and student logins that already know a child's history — all four are blocked by the same line in the schema. Fix that one thing and they stop being four features and become one.

Where the product stands

The examination domain, as it exists today.

A teacher creates a Test, generates an OMR sheet, scans filled sheets, and gets analytics. A Student is a bare roster row — it is not a User and has no login, which is correct and deliberate: marks are entered by the teacher, not the child.

Test exam
  • title, subject, totalMarks
  • organizationId
  • createdBy → User
  • no class link
Student roster
  • name
  • className — String
  • rollNumber — String
  • organizationId
  • userId? · email?
StudentResponse marks
  • testId → Test
  • studentId → Student
  • score, percentage
  • answers → TestAnswer[]

The marks side is sound. StudentResponse hangs off the student and is uniquely keyed on (testId, studentId), so a re-scan updates rather than duplicates. That's the right shape and it's worth keeping.

The root cause

A class is not a thing. It's a string typed on every sheet.

className and rollNumber are plain strings stored on the person. There is no Class model, no AcademicYear, and no enrollment relation. A class only comes into existence as a side effect of someone scanning a sheet and typing 10A into a box.

Everything you want to build runs into this:

What you wantWhy it can't work today
Create a class, enroll students A class has no existence before a test is scanned. The roster is a byproduct, not something you manage.
Promote students each year Changing className rewrites history — see below. Not changing it forks the student.
Roster appears during OMR Test has no class link, so "who should have sat this?" is unanswerable.
Student logs in, sees past results They'd claim one year's row and see one year's marks. The rest belongs to other rows.
Already fixed today

Both OMR paths matched a student on { name, rollNumber, className } — identity including the name. Since the name comes from OCR or retyping, "Suraj Kumar", "suraj kumar" and "Suraj  Kumar" each created a separate roster row holding a slice of one child's marks. Identity is now (org, class, roll) with the name as a mutable attribute. Your data is clean — 0 duplicates across 12 rows — so this was caught before it did damage.

What breaks in April

The year rollover, traced through the current schema.

Priya is roll 12 in class 10A. She sits three tests. In April she moves to 11A and becomes roll 7. There are exactly two things the current model lets you do, and both are wrong. 

// Option A — update the row
Student { name: "Priya", className: "11A", rollNumber: "7" }
   └─ StudentResponse ×3  ← her class-10 marks now claim she was in 11A

   Last year's class analytics silently change. History is corrupted.


// Option B — leave it, let the next scan create a row
Student { name: "Priya", className: "10A", rollNumber: "12" } ─ 3 responses
Student { name: "Priya", className: "11A", rollNumber: "7" } ─ new responses

   One child, two rows, two disconnected histories. Neither is complete.

This is the classic slowly-changing-dimension problem, and it has a deadline: it becomes real the first April after you have customers. Anything built on top of the current model has to be rebuilt after that.

The fix

Separate the person from their place in a given year.

Student becomes the durable person and never changes class. A new Enrollment row records "this student, in this class, in this year, at this roll number". Promotion writes a new enrollment; it never touches the student or their marks.

AcademicYear new
  • name "2026–27"
  • startsOn, endsOn
  • isCurrent
  • organizationId
Class new
  • name "10", section "A"
  • academicYearId
  • classTeacherId?
  • organizationId
Enrollment new · the hinge
  • studentId → Student
  • classId → Class
  • rollNumber
  • status
Student changed
  • fullName
  • admissionNumber
  • userId? · email?
  • – className
  • – rollNumber

Three properties that matter

Roll number moves to Enrollment. A roll number is assigned per class per year — it was never a property of a person. Unique on (classId, rollNumber), which is the real constraint a school enforces.

admissionNumber becomes the durable key. Every school already issues one; it's on the ID card and never changes. That is the stable identifier the current model lacks — (class, roll) is temporary by definition, so it can't anchor identity.

StudentResponse doesn't move. It keeps pointing at Student, so marks survive promotion untouched. To ask "how did 10A do last year", join through the enrollments for that class and year. History becomes a query, not a stored state you have to keep rewriting.

Why this unlocks student login for free

The nullable Student.userId seam already exists. Once identity is durable, a student who claims their roster row inherits everything automatically — every test, every OMR scan, every analytic, across all years — because it was all hanging off one Student the whole time. Without this fix they'd claim one row and see one year. The login feature isn't a separate project; it's a consequence.

What the teacher actually sees

The OMR flow, before and after.

Today a teacher retypes name, class and roll for every single sheet. Roll is auto-filled from detection; name and class never are. With 42 sheets that's 42 rounds of manual entry and 42 chances to fork a roster row.

The endpoint for this already exists: /api/students/suggest now accepts ?className= and returns a whole roster, org-scoped. It's the seam the new UI plugs into.

Sequence

Each phase ships on its own and leaves the product working.

  1. Finish the WorkOS cutover

    Run the user import and the backfill. Not optional — it's what remaps those TemplateForm rows and stamps organizationId everywhere. Everything below assumes org scoping works.

  2. Close the WebSocket hole — struck

    Done then deleted: the handshake was secured with a signed token, and the collaboration feature was subsequently removed altogether. Folders are single-owner. If team sharing returns it should be org-scoped rather than a per-folder ACL.

  3. Add AcademicYear, Class, Enrollment

    Additive and nullable — nothing reads them yet. Backfill a class per distinct (org, className) into a current year, and one enrollment per student at their existing roll.

  4. Class management UI

    Create classes, enroll students, import a roster from CSV. This is the first moment a teacher can set up before scanning anything — the shift from roster-as-byproduct to roster-as-record.

  5. Roster-driven OMR

    Link Test to a class. Detected roll resolves to an enrollment, name fills itself, unmatched rolls get flagged, progress is visible. The manual retyping disappears.

  6. Year rollover

    Bulk-promote a class into the next year's class with new roll numbers. One screen, run once a year, and the feature that makes the whole model pay off.

  7. Student accounts

    Per-class join code — student signs up with any email and enters the code to claim their roster row. Sidesteps the "half of them have no email" problem, and their full history is already attached.

The one thing to take away

Phases 3 through 7 are one project, not five. They all follow from moving class and roll number off the student and onto an enrollment. Every month that ships on the current model is a month of data that has to be migrated later — and the deadline isn't arbitrary. It's the first April you have paying customers.
